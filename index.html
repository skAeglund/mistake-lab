H3 (cold-start guard): when fetchGames' Gist-configured cold-start path calls await loadFromGist() and that returns false (network failure during initial load AND no GIST_PROGRESS_CACHE_KEY in localStorage to fall back to via L6 — true cold start on a new device with transient connectivity), gistData stays null. Pre-H2 this caused total remote-progress-loss on the next syncToGist (blind PATCH'd an empty fresh gistData over Gist's existing state) but H2's read-merge-write closed that vector — syncToGist now refuses to write on read failure. The remaining issue was UX: extractAllMistakes ran against null gistData (no invalidations / notes / practice items in queue this session), the user saw an empty queue, and showMainApp set the status to 'Synced' anyway, suggesting everything was fine. Now fetchGames captures loadFromGist's return value and on false sets a clear 'Progress unavailable — refresh when online' status; the user knows to refresh once connectivity is restored. L2 (status preservation): updateSyncStatusForAirplane now reads dot.classList.contains('error') and short-circuits when an error state is already set, so the 'Progress unavailable' label H3 sets survives the showMainApp call that happens immediately after. Reading the actual DOM rather than tracking a parallel JS variable prevents drift between intended and shown state. L3 (consolidation): the inline status logic in showMainApp (`if (airplaneMode) ... else if (isGistConfigured()) setSyncStatus('ok', 'Synced')`) was a near-verbatim duplicate of updateSyncStatusForAirplane — replaced with a call to the now-error-preserving function so future status-state additions (e.g., a 'reconnecting' state) don't have to be added in two places. Side benefit: removes the brief pre-phase-2 'Synced' flash that happened in the cache-first fast path between phase 1's setSyncStatus('syncing', ...) and phase 2's start.
